# Configuração das contas de serviço

Preparação para o plano `docs/superpowers/plans/2026-10-14-account-community-checkout-plan.md`. Este guia não significa que as integrações foram criadas/validadas. Não enviar segredos no chat, não inserir chaves no frontend e não versionar arquivos de ambiente.

## Vercel

A CLI oficial 64.1.0 está disponível via npm, mas a sessão consultada ainda não estava autenticada. No terminal do projeto, o proprietário pode iniciar o login deliberadamente:

```powershell
rtk proxy npx --yes vercel@64.1.0 login
```

Concluir o login no navegador indicado pela CLI. Não compartilhar o código de autorização. Ao terminar, informar somente que o login foi concluído. Não é preciso comprar domínio nem selecionar plano pago para esta etapa de autenticação.

Depois do login, a implementação conferirá usuário/equipe/projetos antes de vincular o repositório. A instalação do plugin/skill não autentica automaticamente essa CLI. Não criar projetos/recursos repetidos para tentar resolver login. Não aceitar termos em nome do proprietário com flags automáticas.

## Google Cloud: frete e login são configurações diferentes

**Atualização em 15/10/2026:** projeto `biblioconnect-511704` criado; o proprietário aceitou os termos Cloud e a política de dados OAuth. Identidade BiblioConnect criada com contato de suporte aprovado. Cliente Web local criado com autorização explícita, restrito a `http://localhost:5173` e `http://localhost`; usuário proprietário incluído no teste. Biblioteca oficial `google-auth-library` 11.3.0 instalada. O proprietário concluiu o login real e a home autenticada foi conferida no navegador interno. O fluxo usa apenas Client ID público, sem Client Secret, acesso Gmail/Drive ou confirmação adicional para Gmail verificado. A sessão Google continua sendo uma sessão própria do BiblioConnect.

O runtime local carrega o Client ID conferido de configuração privada ignorada pelo Git. O cliente de produção/origem HTTPS ainda precisa ser configurado quando o domínio estiver definido; o cliente local não libera login em qualquer domínio. O aplicativo Google permanece em modo de testes. A tela de Routes API foi aberta, mas ativação/faturamento e credencial restrita ainda precisam ser concluídos antes de declarar frete real validado.

Abrir o [Google Cloud Console](https://console.cloud.google.com/) na conta do proprietário e usar um projeto destinado ao BiblioConnect. A escolha de faturamento/aceitação de termos deve ser concluída pelo proprietário.

**Frete (troca aprovada em 15/10/2026):** usar o plano gratuito Standard do [HeiGIT/openrouteservice](https://account.heigit.org/info/plans). Criar uma única conta, confirmar o e-mail e guardar a chave apenas no backend como `ORS_API_KEY`. Não usar prefixo `VITE_`. O Google continua responsável pelo login; Maps não é mais necessário para o frete.

O backend consulta `https://api.heigit.org/pelias/v1/search` e `/openrouteservice/v2/directions/driving-car/json`, com chave no header Authorization. A origem provisória autorizada é `Rua José de Alencar, 511, Farol, Maceió - AL, Brasil`, variável `STORE_ADDRESS`; tarifas `DELIVERY_BASE_FEE=5.00` e `DELIVERY_PRICE_PER_KM=2.50`. A distância é viária; a duração não considera trânsito ao vivo. Resultado ao nível da rua é identificado como aproximado na tela, com os locais encontrados e atribuição HeiGIT/OSM. Cidade/país sem rua, baixa confiança e nome incompatível são recusados. A compra recalcula o frete no servidor. Limites do plano são compartilhados por prévias e compras: 2.000 rotas/dia (40/min) e 3.000 geocodificações/dia (100/min), conforme o painel consultado; cada cotação atualmente usa duas geocodificações e uma rota. Exceder cota retorna erro, sem estimativa inventada ou contratação de plano pago.

**Login:** configurar aplicação web no Google Auth Platform/credenciais OAuth e tela de consentimento. Cadastrar origens JavaScript locais usadas pelo projeto (`http://localhost:5173`; adicionar `http://127.0.0.1:5173` somente se realmente utilizado) e, depois de definido, o domínio HTTPS do deploy. Não cadastrar origens `*`. Enquanto o app estiver em teste, autorizar as contas de teste necessárias conforme as regras do Google.

Guardar o Client ID como `GOOGLE_CLIENT_ID` no backend. Ele é identificador público e será exposto somente pelo endpoint de configuração pública do app; não é a API key Maps. O fluxo planejado usa ID token do Google Identity Services validado pelo servidor; não requer distribuir Client Secret ao navegador. Solicitar somente identidade básica necessária ao login, sem permissões de Gmail/Drive.

Referências: [configurar Routes API](https://developers.google.com/maps/documentation/routes/get-api-key), [validação de ID tokens](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token), [Google Identity Services](https://developers.google.com/identity/gsi/web/guides/overview).

## Stripe

Usar uma conta/sandbox própria autorizada. Separar publicável (`STRIPE_PUBLISHABLE_KEY`) e segredo do backend (`STRIPE_SECRET_KEY`). O segredo do webhook (`STRIPE_WEBHOOK_SECRET`) pertence ao endpoint/ambiente correto; segredo do listener local não é o segredo do endpoint hospedado.

Habilitar métodos/BRL/Pix conforme elegibilidade da conta. Começar em sandbox e usar somente dados de teste oficiais. Não enviar número de cartão ou CVV no chat. Na implementação, salvar método de pagamento depende da escolha explícita do usuário e usa referência Stripe. Não validar uma cobrança real automática para demonstrar que o código funciona.

A autenticação no plugin Stripe, se disponível, não deve ser presumida como configuração das chaves da aplicação. Confirmar conta, sandbox, permissões e envs reais antes de construir/validar a integração. Referências: [chaves](https://docs.stripe.com/keys), [testes](https://docs.stripe.com/testing), [Pix](https://docs.stripe.com/payments/pix).

## E-mail

Escolher um remetente autorizado. Para produção na Vercel, o plano oferece API HTTP transacional (Resend) mantendo compatibilidade com o SMTP já existente. Resend exige chave e remetente/domínio apropriado; seus limites de conta/teste não equivalem a envio liberado para todos os leitores. SMTP Gmail exige a configuração de segurança/senha de app da própria conta, nunca compartilhar a senha normal.

As variáveis do projeto serão documentadas/validadas sem imprimir valores. A caixa local de arquivos preservada no desenvolvimento não envia e-mail. Testar recebimento no destinatário próprio autorizado e consumo do link; resposta de sucesso do provedor sozinha não comprova entrega na caixa de entrada.

Referências: [Resend e domínios](https://resend.com/docs/dashboard/domains/introduction), [senhas de app Google](https://support.google.com/accounts/answer/185833).

## Banco e imagens hospedados

O plano preserva Prisma/PostgreSQL e transfere cópia conferida do acervo existente. Não é necessário trocar o ORM, recriar os livros manualmente nem fornecer dump pelo chat. Antes da publicação, configurar PostgreSQL hospedado e armazenamento durável; endereço `localhost` não é acessível pelo deploy.

Capas podem ser públicas; retratos do perfil devem ficar privados e ser lidos com autorização. Não colocar backups de usuários ou credenciais em Git. Neon e Blob são preferências do plano, sujeitas à confirmação dos recursos reais disponíveis e à configuração da conta, sem contratar planos pagos automaticamente.

## Conferência sem revelar segredos

Será usado um diagnóstico com nomes das variáveis e indicadores de presença, seguido de chamadas reais de validação apropriadas. Não colar conteúdo de `.env`, tokens de CLI, chaves Stripe/Maps ou credenciais SMTP em mensagens. Para pedir ajuda, informar apenas qual etapa/código de erro ocorreu, sem URL que contenha token.
Após configurar o cliente OAuth real: instalar a biblioteca oficial no backend com npm install google-auth-library, definir GOOGLE_CLIENT_ID e reiniciar. O endpoint /auth/config só habilita o botão se o Client ID e a biblioteca estiverem disponíveis. Validar login real em origem cadastrada antes de considerar a integração pronta.
